⏱ 11:00-13:00. Each capability is an AWS-managed controller: it does not run on our nodes and we do not upgrade it. Each one assumes its own IAM capability role, named after the cluster: encabulator-usw2-argocd, -ack and -kro, all trusting capabilities.eks.amazonaws.com. ACK's role holds the AWS permissions: RDS and ElastiCache, plus the VPC, IAM and EKS calls it needs to build a new region in Act 3, limited to us-west-2 and us-east-2 and to the cell's own cluster and roles. Argo CD reads a public Git repo, so its role needs no AWS permissions. kro makes no AWS calls; it needs Kubernetes RBAC for whatever its RGDs create.

Build 4: Terraform creates all three in capabilities.tf (aws_eks_capability, AWS provider 6.68). It also creates each capability's access entry first, so the entries carry our tags and kro's carries the Kubernetes group encabulator:kro, which our RBAC binds instead of a role ARN. EKS then adds each capability's default access policies to the existing entry.

Live: aws eks describe-capability --cluster-name encabulator-usw2 --capability-name kro --query capability.status shows ACTIVE.

Adopt, don't rebuild

⏱ 13:00-15:00. The database does not move and is not recreated. Build 1: ACK starts managing the existing instance through a DBInstance custom resource. Two ways to adopt

adopt
Import it exactly as it is
AWS→spec

ACK writes what it finds into your spec. Nothing in AWS changes.

adopt-or-create
Your YAML is the truth
spec→AWS

Adopts it if it exists and makes it match. Creates it if it doesn't.

Recipe: adopt to read the spec → commit it to Git → adopt-or-create in every region

⏱ 19:00-20:00. adopt is the safe first look: AWS is the source, your spec is filled in. adopt-or-create is the steady state: your manifest wins, and in a region where the resource does not exist yet, ACK creates it. That second property is what lets one definition serve both regions later.

One API for the whole stack

⏱ 26:00-28:00. The idea of the act. A platform team publishes one API, Encabulator. A developer (or Argo CD) creates one object. kro expands it into everything: the three AWS resources through ACK (DBSubnetGroup, DBInstance, ServerlessCache), and the Kubernetes objects: the encabulator-aws ConfigMap, NATS and InfluxDB StatefulSets and fifteen services. It also creates a StorageClass and two one-time Jobs: one generates the passwords and keys, one creates the three databases on RDS. The service itself is a second, smaller API (EncabulatorService); RGDs chain. Each service gets a ServiceAccount, a Deployment and a Service, plus an HPA, a PodDisruptionBudget or a Role where the chart gave it one.

⏱ 45:00-47:00. The cluster generator watches Argo CD cluster Secrets. Label the Secret (kro already did) and an Application appears for that cluster. With goTemplate, {{ .name }} is the Secret's name, so the Application is called encabulator-use2, and {{ .server }} is the cluster ARN. Build 3: region-specific values never enter Git. Two kustomize patches copy the Secret's annotations into the instance (spec.subnetIDs, spec.securityGroupID) and into the NodeClass. missingkey=error fails the render if an annotation is missing instead of rendering an empty value. The third patch is optional: when the Secret carries encabulator.io/registry, it sets spec.registry and every image comes from that registry (a mirror, for example); without it the RGD default applies. Day 2: three reconcile loops

⏱ 53:00-56:00. LIVE. Build 2: delete a Deployment in the cell (kubectl --context use2 -n encabulator delete deployment ...); kro owns it through its EncabulatorService and puts it back within seconds, and Argo CD above it keeps the instance itself in line with Git. Build 3: change dbInstanceClass in gitops/app/instance/encabulator.yaml, push, and the RDS instance moves to Modifying. That file is shared by every cell, so the change rolls out to all of them.

Presenter tip: because kro puts back every field it sets, the console's Malaise scale fault (for example scaling a service to zero) is reverted on a cell at kro's next reconcile, for every Deployment with a fixed replica count. On a cell, use the pod-kill or partition faults instead. scale still behaves as before on the hub, where the app is the Helm chart.

Changes made directly in AWS are corrected on ACK's resync period, which the EKS docs put at up to 10 hours, so do not try that one live.

⏱ 56:00-57:30. The six things to take home. Capability roles: the ACK role only needs the AWS services your RGDs use; here it is limited to two regions and to the cell's own cluster and IAM roles, so it cannot change the hub or widen its own permissions. kro needs RBAC for the kinds its RGDs create, bound to a Kubernetes group on its access entry (encabulator:kro) so no role ARN or account id ends up in Git. Argo CD runs as cluster admin on the hub and the cells in this demo; scope it with namespaced access policies or RBAC for production (AmazonEKSClusterAdminPolicy is for getting started only).
