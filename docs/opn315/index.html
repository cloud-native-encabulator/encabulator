⏱ 11:00-13:00. Each capability is an AWS-managed controller: it does not run on our nodes and we do not upgrade it. Each one uses an IAM capability role. ACK's role holds the AWS permissions (RDS, ElastiCache, EKS). Argo CD's role reaches Git and remote clusters. kro makes no AWS calls; it needs Kubernetes RBAC for whatever its RGDs create.

Live: aws eks describe-capability --cluster-name encabulator-usw2 --capability-name kro --query capability.status shows ACTIVE. We created all three yesterday.

Adopt, don't rebuild

⏱ 13:00-15:00. The database does not move and is not recreated. Build 1: ACK starts managing the existing instance through a DBInstance custom resource. Build 2: Terraform stops tracking it, with a removed block that drops it from state and does not destroy it. Build 3: the custom resource lives in Git, so Argo CD owns it from now on.

Point ACK at what already exists

apiVersion: rds.services.k8s.aws/v1alpha1
kind: DBInstance
metadata:
  name: encabulator-pg
  annotations:
    services.k8s.aws/adoption-policy: adopt
    services.k8s.aws/adoption-fields: |
      {"dbInstanceIdentifier": "encabulator-pg"}
    services.k8s.aws/deletion-policy: retain
# no spec: ACK reads it back from AWS

⏱ 15:00-19:00. LIVE. Type or paste the manifest. The two highlighted annotations do the work: the adoption policy, and the field ACK uses to find the instance. No spec at all; with adopt, ACK fills it in from the real instance.

Build 1: apply and watch READY go True. Build 2: kubectl get dbinstance encabulator-pg -o yaml | yq .spec. That spec is now the source we commit to Git. Build 3: always add the retain annotation before you touch anything that holds data.

Two ways to adopt

adopt
Import it exactly as it is
AWS→spec

ACK writes what it finds into your spec. Nothing in AWS changes.

adopt-or-create
Your YAML is the truth
spec→AWS

Adopts it if it exists and makes it match. Creates it if it doesn't.

Recipe: adopt to read the spec → commit it to Git → adopt-or-create in every region

⏱ 19:00-20:00. adopt is the safe first look: AWS is the source, your spec is filled in. adopt-or-create is the steady state: your manifest wins, and in a region where the resource does not exist yet, ACK creates it. That second property is what lets one definition serve both regions later.

One API for the whole stack

⏱ 26:00-28:00. The idea of the act. A platform team publishes one API, Encabulator. A developer (or Argo CD) creates one object. kro expands it into everything: the AWS resources through ACK, and the Kubernetes objects. The service itself is a second, smaller API (EncabulatorService); RGDs chain.

The schema is the API

apiVersion: kro.run/v1alpha1
kind: ResourceGraphDefinition
metadata:
  name: encabulator
spec:
  schema:
    apiVersion: v1alpha1
    kind: Encabulator
    spec:
      imageTag: string | default="1.0.0"
      dbInstanceClass: string | default="db.t4g.medium"
      subnetIDs: "[]string"
      securityGroupID: string | required=true
      services: "[]string"
    status:
      databaseHost: ${db.status.endpoint.address}
      cacheHost: ${cache.status.endpoint.address}
  
kubectl apply -f rgds/encabulator.yaml
kubectl explain encabulator.spec
FIELDS:
  dbInstanceClass   <string>

  securityGroupID   <string> -required-

  subnetIDs         <[]string>
kro turns the schema into a real CRD: types, defaults, validation.
Status is computed from the resources it creates.

⏱ 31:00-34:00. The same adopt-or-create and retain annotations from Act 1, now inside the template. In a region where encabulator-pg already exists, ACK adopts it; in a new region it creates it. Each ${...} that points at another resource is an edge in the graph: the DBInstance waits for the subnet group, and the ConfigMap waits until the database reports an endpoint.

The ConfigMap that Terraform used to write is now produced by kro from the ACK status, under the same name, so the services do not change.

Hub and spoke

⏱ 40:00-42:00. The hub runs all three capabilities. Build 1: one more kro API on the hub, EncabulatorCell: one object per region. Build 2: ACK on the hub creates the new EKS cluster and its ACK and kro capabilities in us-east-2 (the EKS controller has Cluster, Capability and AccessEntry kinds). Build 3: kro also writes the Argo CD cluster Secret, so an ApplicationSet picks up the new cluster and syncs the Encabulator instance to it. Build 4: ACK on the cell creates RDS and ElastiCache in its own region. Green field, no Helm, no Terraform.

A new region is one object

- id: cluster
  template:
    apiVersion: eks.services.k8s.aws/v1alpha1
    kind: Cluster
    metadata:
      name: ${schema.metadata.name}
      annotations:
        services.k8s.aws/region: ${schema.spec.region}
    spec:
      name: ${schema.metadata.name}
      # role, VPC config, Auto Mode ...
- id: kroCapability
  template:
    apiVersion: eks.services.k8s.aws/v1alpha1
    kind: Capability
    spec:
      clusterName: ${cluster.spec.name}
      type: KRO
      deletePropagationPolicy: RETAIN
  
- id: register
  template:
    apiVersion: v1
    kind: Secret
    metadata:
      name: ${schema.metadata.name}
      namespace: argocd
      labels:
        argocd.argoproj.io/secret-type: cluster
        encabulator.io/cell: "true"
    stringData:
      name: ${schema.metadata.name}
      server: ${cluster.status.ackResourceMetadata.arn}
      project: default
Argo CD addresses EKS clusters by ARN. kro reads the ARN from the ACK status.

⏱ 42:00-45:00. Build 1: the EKS Cluster, created by the hub's ACK in the region named on the instance. Build 2: an ACK Capability for kro on the new cluster (the ACK capability is the same block with type ACK). An AccessEntry for the Argo CD capability role is the remaining piece, also an ACK kind. Build 3: the Argo CD cluster Secret. The EKS Argo CD capability takes the cluster ARN as server, and kro fills it in from the ACK status. Build 4: so registering a cluster is just another resource in the graph.

Day 2: three reconcile loops

⏱ 53:00-56:00. LIVE. Build 2: delete a Deployment in the cell; kro (and Argo CD above it) puts it back. Build 3: change dbInstanceClass in the instance, push, and the RDS instance moves to Modifying.
